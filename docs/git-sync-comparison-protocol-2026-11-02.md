# Git 增量同步版本对照测评

这套测评比较 Git 增量同步初版与当前版本，回答“已有增量同步之后，阶段缓存和失效范围拆分带来了什么”。全量重建不作为主对照；初版已有向量复用、持久任务和版本发布，这些能力不能重复记为新版收益。

## 固定对照与隔离

- 主对照：完整 `576d093` 后端与运行时指定的当前提交；两者完整 SHA 写入报告。
- 两版本运行各自的源码，使用同一 Python 与已安装依赖。没有重建历史依赖环境，因此属于受控源码比较。
- 每组使用独立子进程、SQLite、Chroma、任务表、快照和缓存目录。不读取生产知识库，不执行生产建表或迁移。
- 将 `embed_texts` 替换为文本确定性映射的 1024 维向量，SDK 客户端另设禁止调用的保护。它保留真实解析、切分、索引读写、BM25 构建与发布校验；不测供应商批处理、重试、网络延迟、语义召回或账单。

## 计量协议修订

第一批 240 个试验采用 v1：为了固定处理版本指纹，预先计算并冻结 profile。复核发现解析、切分、嵌入和写入的计数包装并不会改变原生指纹；冻结并非必要，而且省去了生产中的重复源码读取和哈希，两个版本省掉的工作量不同。因此 v1 的 wall/CPU 数据只能标为“预计算指纹适配下的生命周期耗时”，不能直接称为原生端到端耗时。计算量、发布结果和原始 Chroma upsert 包含时间仍按该实验口径保留。

v2 默认 `--profile-mode native`，保留原生 profile 计算；包装计数前后检查同一源码版本的指纹值一致，身份检查在计时外，随后清零该检查带来的计数。`--profile-mode precomputed` 用于复现旧口径。profile 时间包含嵌套调用，不能把多个 profile 的累计时间相加。

两种模式的报告分别保存，不合并统计。另补 64 篇三轮无变化/解析指纹变化、512 篇一轮无变化的 native 校准；512 篇一对样本只用于核对计量路径，不作为稳定性能或微小提升证据。少于三对时不生成 bootstrap 区间。

## 数据与规模

每轮保留项目的 16 篇 IT 文档，其余从本地已有的 10,000 篇 CRUD-RAG 衍生文本中抽样。正文不改，只补齐受控的文档身份和 frontmatter。按长度四分位抽样，并额外加入约 1/16 的 top-1% 长尾文档。这样能覆盖长短文开销，但不是企业 IT 文档的真实流量分布。

默认规模为 64、256、512 篇，每档五轮，逐轮更换固定种子；同轮两版本输入完全相同。报告保存样本路径、原始 SHA-256、输入摘要、总字节、长短分布和唯一正文数。源正文留在本地输出目录，不应上传到仓库。

不放宽产品限制：最多 512 篇、单篇 2 MiB、原文合计 16 MiB。超过这些限制应单独测拒绝行为，不能作为已支持规模。样本池有一万篇不表示本次同时同步了一万篇。

## 工作负载与缓存状态

每个版本、规模、重复轮次先完成一次冷构建；等子进程退出后复制该工作目录，每个变更都从同一个暖模板独立分叉。复制和快照路径重定位在计时外。不同场景不能相互预热。

| 场景 | 输入变化 | 要核验的行为 |
| --- | --- | --- |
| cold | 全新应用缓存与数据库 | 首次构建成本，不预设新版更快 |
| unchanged | 文档字节相同，使用新提交 | 不能靠同任务幂等直接返回；比较实际解析和切分次数 |
| body_1pct / body_10pct | 对向上取整的 1% / 10% 文档追加一条记录 | 对比相同改动的嵌入与写入，不概括为任意章节编辑 |
| metadata_10pct | 只增加元数据修订字段 | 正文和向量不应变化，元数据不能陈旧 |
| rename_10pct | 改路径，保留身份与正文 | 复用向量，同时更新来源路径 |
| delete_10pct | 删除部分文档 | 发布后无旧块残留，剩余正文完整 |
| parser_source_change | 只追加解析模块源码注释，解析输出不变 | 直接触发各版本原生源码指纹；观察失效是否扩散到切分与嵌入 |

解析源码变更场景只证明这一种“指纹变、输出不变”的升级，不证明所有解析器升级都应复用结果。没有输入变化的场景仍会创建新一代索引；本实验保留这个真实成本。

## 计量与正确性

计时从入队到构建和校验发布完成，另外记录入队、处理、发布三段。源输入生成、进程导入、目录复制与独立正确性校验不计入同步耗时。操作系统页缓存未清除；“冷”仅指应用缓存、数据库和索引为空。版本顺序按 AB/BA 交替，测评子进程串行运行。

记录 wall time、进程 CPU time、解析/切分函数执行次数、嵌入输入条数及 UTF-8 字节、索引 upsert 次数与块数。函数执行次数包括同篇文档在发现、快照持久化、构建和发布核验中的重复工作，不能当作不同文档数量。进程 RSS 是累计峰值，包含导入与准备，不是单次操作净增量。存储是工作目录逻辑文件字节，包含保留代、快照、输入和缓存，不是实际分配磁盘块。

计时后直接读取 raw Chroma 数据，独立于缓存与 manifest 的自报数量，检查：

- 来源身份、完整父正文、路径及源元数据；
- 实际块集合与 manifest 摘要、发布指针；
- 子块归属、按章节和片段位置连接后的有序正文覆盖，包含标题和重复内容；短引言按现有切分约定不进入子块；
- 子向量由独立确定性函数重新计算，与实际向量归一后按 `2e-6` 容差核对，父向量为零；
- 文档删除后没有额外的旧文档和旧块。

正确性不通过的轮次必须保留。统计显示每组尝试数、失败数及完整配对数，速度比只在同轮双方都成功时计算，不能用幸存样本掩盖失败。

## 统计与结论边界

每组给出中位数、四分位区间和极值；配对速度比为旧版耗时 / 新版耗时。五轮 bootstrap 区间只作探索性描述，不宣称稳定 p95、生产 SLO 或统计显著。真实同步总耗时可能几乎不变，甚至变慢；解析调用下降不等于总耗时同比下降，嵌入输入减少也不等于供应商 API 请求数或费用同比下降。

故障重试、进程恢复、备份和保留策略另有专项测试与演练。这组正常路径性能实验不能替代它们，也不独立证明缓存、重试、清理各自的因果贡献；若要做归因，还需增加消融组。

补充的当前版本故障矩阵使用同一份 64 篇语料，每例独立重建临时 SQLite/Chroma，覆盖阶段缓存损坏、向量缓存损坏、503 持久退避、401 不重试、部分写入、不完整候选、过期 prepared 拒绝发布、删除后失败/回滚，以及 prepared 后候选向量被替换为合法维度错误数值。除 raw/元数据视图，还检查实际 query 和 get_by_ids 的删除限制；回滚必须真的互换 active/previous 并递增意图序号。

故障矩阵明确保留未通过项：prepared 后底层向量被替换为有限的 1024 维错误向量，当前发布校验仍可能放行。独立向量 oracle 会将该例记为失败。这说明现有契约没有绑定构建完成后的向量内容摘要，不等于正常同步会自行生成错误向量。503 使用应用时钟推进验证等待门禁，不测真实等待或恢复时延。

## 复现

```bash
.venv/bin/python backend/scripts/eval_sync_comparison.py \
  --sizes 64 256 512 --repeats 5 \
  --profile-mode native \
  --output-dir /tmp/itdesk-sync-paired-run
```

复现首批 v1 的受控计量范围应显式选择 `--profile-mode precomputed`，不能将其输出标为 native。原始计量脚本及 SHA-256 和完整数据一起在本地归档。

```bash
.venv/bin/python backend/scripts/eval_sync_resilience.py \
  --input-corpus /tmp/itdesk-sync-paired-run/inputs/n64-r0-current-cold.json \
  --backend-root "$PWD/backend" --output /tmp/sync-resilience.json
```

输出包含逐轮 JSON、错误日志、输入、样本 manifest 和汇总 `report.json`。目录必须没有既有报告，避免将不同协议运行混为一组。运行需要现有本地外部语料；缺失时明确失败，不自动下载或换成重复模板。
